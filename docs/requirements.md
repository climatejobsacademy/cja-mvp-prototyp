# System Requirements — AfCJ MVP-Prototyp

Auszug aus der Notion-Datenbank „System Requirements“, Stand 03.11.2026. Diese Datei wird nicht von Hand geändert: Änderungen und neue SRs gehören in Notion, die Nummer vergibt Notion, und der Auszug wird danach neu erzeugt. Der Auszug enthält Nummer, Titel (Feld „Requirement“), Typ und Acceptance Check im Wortlaut von Notion; Stage, Status und Prototyp-Rolle führt nur Notion. Wo was gepflegt wird, steht auf der Notion-Seite [Quellen und Arbeitsteilung: was wo lebt](https://app.notion.com/p/40c48915565b81829be7e58700050f58); die Zuordnung zu Pull Requests steht in `traceability.md`.

| SR-ID | Titel | Typ | Acceptance Check |
|---|---|---|---|
| SR-01 | Das System berechnet den Erfüllungsstatus einer Kompetenz ausschließlich aus dem Abschluss-Status ihrer Teilschritte; ein manuelles Bearbeiten des Kompetenzstatus ist nicht möglich | Data | Alle Teilschritte einer Testkompetenz auf 'erfüllt' setzen → Kompetenz zeigt 100%. Es existiert kein Formularfeld oder API-Endpunkt, der den Kompetenzstatus direkt schreibt. |
| SR-02 | Ein Learner kann für eine abgeschlossene Praxisaufgabe in der mobilen Feld-Ansicht (PWA) eine Selbstauskunft einreichen, die mindestens einen Teilschritt referenziert und einen Zeitstempel erhält | Functional | Learner reicht Selbstauskunft für einen Feldjob ein → Datensatz mit Status 'submitted', Zeitstempel und mind. einer Teilschritt-Referenz ist gespeichert und für den Learner in seinem eigenen Profil sichtbar. |
| SR-03 | Nur AfCJ admin (Prototyp) oder die zuständige Instructor-Rolle (ab MVP) können den Status einer Selbstauskunft von 'submitted' auf 'verified' oder 'rejected' ändern; der einreichende Learner selbst kann seine eigene Selbstauskunft nicht verifizieren | Access / Security | Versuch des Learners, die eigene Selbstauskunft zu verifizieren → wird abgelehnt (403 bzw. RLS-Policy-Verstoß). AfCJ admin kann denselben Datensatz verifizieren. |
| SR-04 | Teilschritte und ihre Belege (Content-Einheit oder Praxisaufgabe) werden als N:M-Zuordnung gespeichert, sodass ein Teilschritt mehrere Belege aus verschiedenen Curricula referenzieren kann und ein Beleg auf mehrere Teilschritte einzahlen kann | Data | Import von mind. 3 Kompetenzen aus der hochgeladenen Kompetenzmatrix inkl. eines Teilschritts mit 2+ Belegen unterschiedlicher Quelle → jede Beleg-Zuordnung ist als eigener Datensatz gespeichert, ohne den Teilschritt zu duplizieren. |
| SR-05 | Lerninhalte sind in einer vierstufigen Hierarchie Qualifikationsprogramm → Modul → Kurs → Lektion organisiert, getrennt von der Kompetenz-Hierarchie (Kompetenz → Teilschritt) und mit ihr über eine eigene N:M-Zuordnungstabelle verknüpft | Data | Test: eine Lektion aus zwei verschiedenen Modulen referenzierbar, ohne dupliziert zu werden. |
| SR-06 | Keine API-Antwort, Datenbankabfrage oder Export liefert jemals Datensätze, deren organization_id vom anfragenden Betrieb abweicht — mit Ausnahme AfCJ-eigener (geteilter) Entitäten sowie der Rollen AfCJ admin und AfCJ trainer | Access / Security | Automatisierter RLS-Test: Nutzer aus Betrieb A fragt Datensätze von Betrieb B ab → leeres Ergebnis, kein Fehler mit Informationsgehalt. Test läuft in CI für jede employer-owned Tabelle. |
| SR-07 | Anwesenheits- und Fortschrittsdatensätze (bestätigte Teilnahme, verifizierte Selbstauskünfte, abgeschlossene Lerneinheiten) sind nach Bestätigung unveränderlich und mit Zeitstempel sowie handelnder Person gespeichert, damit sie AZAV-Nachweisprüfungen standhalten | Non-functional | Versuch, einen bestätigten Anwesenheits- oder Verifizierungsdatensatz nachträglich zu ändern → vom System verhindert (DB-Trigger). Jeder Datensatz zeigt Zeitstempel und handelnde Person im Export. |
| SR-08 | Schreiboperationen im Feld-Workflow (Selbstauskunft, Foto-Upload) sind klein und in sich abgeschlossen, sodass sie bei unterbrochener Mobilverbindung (schwaches Signal im Zählerschrank) wiederholt werden können, ohne Daten zu verlieren oder zu duplizieren | Non-functional | Simulierter Verbindungsabbruch während einer Selbstauskunft-Einreichung → Wiederholung des Requests führt zu genau einem gespeicherten Datensatz, nicht zu keinem oder zu doppelten. |
| SR-09 | Für jeden Teilschritt-Typ (Content-Einheit, Live-Veranstaltung, Praxis-Teilschritt) speichert das System einen binären Nachweisstatus (erbracht / nicht erbracht) mit Zeitstempel und der Person, die ihn gesetzt hat | Data | AfCJ admin markiert im Backend eine Lektion, einen Kurs, eine Live-Session-Teilnahme und einen Praxis-Teilschritt jeweils als erbracht → alle vier Nachweisstatus sind einheitlich strukturiert (gleiche Felder: Status, Zeitstempel, gesetzt von) abrufbar. |
| SR-11 | Das Datenmodell sieht vor, dass ein Nachweisstatus künftig durch Foto-, Video- oder Sprachdatei-Anhänge ergänzt werden kann, ohne die Struktur des Prototyps zu ändern; implementiert wird dies erst, sofern sich mediale Nachweise als sinnvoll erweisen | Data | Die Nachweis-Tabelle enthält bereits (leere) Felder für Medientyp und Medien-URL, auch wenn im Prototyp nur Boolean/Text geschrieben wird; Aktivieren von Medien-Uploads später erfordert kein Redesign der Tabelle. |
| SR-12 | Die gesamte Plattform ist übersetzbar (via Sprachauswahl); die Sprachauswahl gilt pro Account und persistiert zwischen Sitzungen | Functional | Systemsprache auf Ukrainisch stellen → alle Kernbildschirme (Day View, Programmübersicht, Content Library) zeigen ukrainischen Text; fehlende Übersetzungen fallen sichtbar auf Deutsch zurück statt einen Platzhalter oder Fehler zu zeigen. |
| SR-13 | Der Learner sieht eine Tagesansicht, die alle für den aktuellen und folgenden Tag geplanten Aktivitäten (Live-Session, Selbstlerneinheit, Praxistag) chronologisch mit Typ, Uhrzeit und Zugangsweg anzeigt | Functional | Learner mit gemischtem Tagesplan (Live-Session um 9 Uhr, Selbstlerneinheit, Praxistag am Nachmittag) sieht alle drei Einträge chronologisch sortiert mit Typ-Kennzeichnung in einer Tagesansicht. |
| SR-14 | Der Learner kann eine Content-Bibliothek einsehen, durchsuchen und nutzen, die alle für sein Qualifikationsprogramm freigegebenen Lerneinheiten einhält | Functional | Learner ruft Content Library auf → Liste aller ihm zugänglichen Lerneinheiten (gefiltert nach seinem Qualifikationsprogramm) mit Titel, Typ und Abschlussstatus wird angezeigt; Klick öffnet die Einheit direkt. |
| SR-15 | Für jede geplante Live-Session sieht der Learner Datum, Uhrzeit und einen direkten Beitritts-Link zum externen Video-Tool | Functional | Für eine geplante Live-Session zeigt die Detailansicht Datum, Uhrzeit und einen funktionierenden Beitritts-Link; Klick führt direkt zum externen Video-Tool ohne weiteren Login-Schritt. Ergänzt 12.10.: Angezeigt werden ausschließlich Termin und Link der eigenen Kohorte, auch wenn mehrere Kohorten dieselbe Lektion nutzen (Test: zwei Kohorten, gleiche Lektion, unterschiedliche Termine → jede Person sieht nur ihren Termin). |
| SR-16 | Ein Learner meldet sich ausschließlich per Magic-Link-E-Mail an; es gibt im Prototyp keinen passwortbasierten Login | Functional | Login-Versuch mit E-Mail-Adresse → Magic-Link-E-Mail wird versendet, Klick auf den Link meldet den Nutzer ohne Passworteingabe an. Kein Account ohne vorherige Einladung/Anlage durch AfCJ admin möglich. |
| SR-17 | Das System trackt und berechnet die kumulierte reale Lernzeit (aus Content-Bearbeitung und Live-Session-Teilnahme); im Prototyp primär zur internen Analyse durch AfCJ, nicht zwingend learner-facing | Data | Nach Abschluss einer Lerneinheit und einer Live-Session-Teilnahme liegt die kumulierte Lernzeit in Stunden als berechneter Wert vor (aus den einzelnen Aktivitätszeitstempeln, nicht aus einer manuell gepflegten Zahl) und ist für AfCJ admin einsehbar/exportierbar zur Analyse. Eine Learner-facing Anzeige ist im Prototyp nicht erforderlich — ob und wie das später Lernenden gezeigt wird, ist noch offen. |
| SR-18 | Ein Manager kann für einen Mitarbeitenden seines Betriebs die granulare Kompetenzansicht auf Teilschritt-Ebene einsehen, nicht nur einen aggregierten Gesamtstatus | Functional | Manager ruft Kompetenzansicht eines Mitarbeitenden auf → sieht Liste der Kompetenzen mit Status je Teilschritt (erbracht/offen), nicht nur eine pauschale Prozentzahl oder ein Zertifikat. |
| SR-19 | AfCJ admin kann im Backend einen neuen Betrieb mit Namen, Ansprechperson und Mitarbeitenden-Accounts anlegen | Functional | Admin legt neuen Betrieb mit zwei Mitarbeitenden-Accounts an → beide erhalten eine Magic-Link-Einladung und können sich als Learner der richtigen Organisation anmelden, ohne dass Entwicklung involviert wird. |
| SR-20 | AfCJ admin kann eine Kohorte für ein Qualifikationsprogramm anlegen und Learner diesem Programmdurchlauf zuordnen | Functional | Admin erstellt eine Kohorte für ein Qualifikationsprogramm und ordnet drei Learner zu → alle drei sehen dieselbe Programmübersicht und denselben Schedule-Rahmen. |
| SR-21 | AfCJ Admin kann eine Live-Session mit Datum, Uhrzeit, Video-Link und Kohorten-Zuordnung anlegen; sie erscheint automatisch in der Tagesansicht der zugeordneten Learner | Functional | Admin legt eine Live-Session mit Datum, Uhrzeit, Video-Link für eine Kohorte an → alle Kohorten-Mitglieder sehen den Termin automatisch in ihrer Tagesansicht (SR zu UN-27), ohne manuelles Eintragen durch den Learner. |
| SR-22 | AfCJ admin kann eine aggregierte, betriebsübergreifend vergleichbare Übersicht über Programmstatus und Kompetenzfortschritt aller User in allen Betriebe abrufen | Functional | Admin ruft die betriebsübergreifende Übersicht auf → Tabelle mit einer Zeile je Betrieb, inkl. Anzahl aktiver Learner und durchschnittlichem Kompetenzfortschritt, ohne einzelne Betriebe manuell nacheinander öffnen zu müssen. |
| SR-23 | AfCJ admin kann eine Repository-Datei als Wissensquelle (Norm, SOP, Herstellerdokument) markieren und mit einem Freigabestatus versehen; nur freigegebene Quellen werden vom Feld-Guidance-System durchsucht und zitiert | Functional | Admin markiert eine Repository-Datei als Wissensquelle und setzt Status 'Entwurf' → Dokument erscheint nicht in Guidance-Antworten. Setzt Status auf 'freigegeben' → Dokument wird durchsucht und bei passender Frage mit Quellenangabe zitiert. |
| SR-24 | Der Learner kann Fachbegriffe (Normen, DGUV, VDE) im Lerncontent anklicken und erhält eine kontextuelle Erklärung in einfacher Sprache | Functional | Klick auf einen markierten Fachbegriff in einer Lerneinheit öffnet ein Tooltip/Panel mit Erklärung in einfacher Sprache, ohne die Einheit zu verlassen; funktioniert für mind. 20 vordefinierte Begriffe im Testcontent. |
| SR-25 | Während eines praktischen Einsatzes sieht der Learner, welcher Nachweistyp für den aktuellen Praxis-Teilschritt gilt und was als Nächstes ansteht | Functional | In der Feldansicht zeigt jeder offene Praxis-Teilschritt seinen Nachweistyp (aktuell: Selbstauskunft) und den nächsten offenen Schritt der zugehörigen Kompetenz. |
| SR-26 | Der Umfang angezeigter Hilfetexte pro Aufgabe hängt vom bisherigen Kompetenzfortschritt des Learners in der zugehörigen Kompetenz ab | Functional | Zwei Learner mit unterschiedlichem Fortschritt in derselben Kompetenz sehen bei identischer Aufgabe unterschiedlich ausführliche Hilfetexte (mehr bei niedrigem, weniger bei hohem Fortschritt). |
| SR-27 | Beim Onboarding kann für einen Learner ein Startzustand mit bereits anerkannten Kompetenzen/Teilschritten hinterlegt werden, sodass die Fortschrittsanzeige nicht bei null beginnt | Data | Admin markiert bei Onboarding 5 Teilschritte als bereits erbracht → Fortschrittsanzeige des Learners zeigt diese sofort als erledigt, nicht als offen, ohne dass der Learner sie erneut bearbeiten muss. |
| SR-28 | Ein Learner oder Admin kann im Ausland erworbene informelle Praxiserfahrung als Freitext-Angabe erfassen, die anschließend Teilschritten zugeordnet und als Nachweis anerkannt werden kann | Functional | Erfasste Angabe erscheint in einer Prüfliste für Admin; Zuordnung zu mind. einem Teilschritt möglich; danach zeigt der Teilschritt den Status 'erbracht' mit Quelle 'anerkannte Vorerfahrung'. |
| SR-29 | Bei jedem Qualifikationsprogramm zeigt das System, für welchen Geltungsbereich (z. B. IHK-Zertifizierung) der Abschluss gilt | Data | Programmübersicht enthält ein sichtbares Feld/Badge mit dem Zertifizierungsstatus (z. B. 'IHK-anerkannt' / 'nicht IHK-anerkannt') des jeweiligen Qualifikationsprogramms. |
| SR-30 | Learner können andere Mitglieder ihrer Kohorte mit Namen und Profilbild einsehen | Functional | Kohortenliste zeigt allen zugeordneten Learnern die anderen Mitglieder derselben Kohorte mit Basisprofil (Name, Profilbild). |
| SR-31 | Der Tagesplan enthält täglich mindestens eine kurze Sprachlern-Einheit, die als eigener Content-Typ im selben Fortschritts-Tracking wie andere Lerneinheiten geführt wird | Functional | Tagesansicht zeigt mind. eine Sprachlern-Aktivität pro Tag; deren Abschluss zählt zur kumulierten Lernzeit wie jede andere Lerneinheit (SR zu UN-33). |
| SR-32 | Beim Anlegen eines Learner-Accounts wird ein Qualifizierungspfad (z. B. EFK-EE oder TQ-EGT) hinterlegt, der bestimmt, welche Module und Kompetenzen dem Learner angezeigt werden | Data | Zwei Learner mit unterschiedlichem hinterlegtem Qualifizierungspfad (EFK-EE vs. TQ-EGT) sehen unterschiedliche Programmübersichten und Content-Bibliotheken, gefiltert nach ihrem Pfad. |
| SR-34 | Ein Manager kann betriebsspezifische Zusatzinhalte (Prozesse, Software-Anleitungen) hochladen, die nur den Mitarbeitenden des eigenen Betriebs angezeigt werden | Functional | Von Manager A hochgeladener Inhalt ist für Learner aus Betrieb A sichtbar, für Learner aus Betrieb B nicht (folgt aus der Tenancy-Isolation-SR). |
| SR-35 | Ein Manager sieht für seine Mitarbeitenden die geplanten Berufsschul- und Praxistermine im Voraus, um Freistellungen planen zu können | Functional | Manager-Ansicht zeigt Kalender/Liste der kommenden Berufsschul- und Praxistermine je Mitarbeitendem für mind. die nächsten 4 Wochen. |
| SR-36 | Ein Manager kann für seine eigenen Mitarbeitenden interne Praxiseinsätze auf Basis von deren Kompetenzprofilen planen | Functional | Manager gibt Mindestkompetenzen für einen geplanten Einsatz ein → System listet passende Mitarbeitende aus dem eigenen Betrieb, gefiltert nach Kompetenzstand. Rein betriebsintern, keine betriebsübergreifende Sichtbarkeit nötig — früher fälschlich als Job-Matching mit externen Absolvent:innen formuliert (Klärung 2026-09-04). |
| SR-37 | Verifizierte Feld-Selbstauskünfte werden automatisch dem entsprechenden TQ-Nachweisformat zugeordnet, ohne dass ein Manager sie manuell in ein externes Dokument überträgt | Data | Eine verifizierte Feld-Selbstauskunft erscheint automatisch im TQ-Nachweis-Export (SR-20) ohne manuellen Übertragungsschritt durch den Manager. |
| SR-38 | Ein Manager kann für einen Mitarbeitenden einen Nachweis-Export erzeugen, der die verifizierten Kompetenzen und zugehörigen Belege in einem für externe Prüfstellen lesbaren Format zusammenfasst | Functional | Manager erzeugt für einen Mitarbeitenden einen Export → PDF/strukturierte Datei mit allen verifizierten Kompetenzen, zugehörigen Belegen und Zeitstempeln liegt vor. |
| SR-39 | Die Systemarchitektur sieht eine offene Schnittstelle vor, über die Betriebsdaten mit externer Handwerkersoftware (z. B. STREIT, HERO) ausgetauscht werden können; die konkrete Anbindung wird erst gebaut, wenn ein Pilotbetrieb sie benötigt | Non-functional | Architektur-Review bestätigt, dass eine offene API-Schicht für Betriebsdaten vorgesehen ist, auch wenn keine konkrete STREIT/HERO-Anbindung im Prototyp gebaut wird. Konkrete Umsetzung erst bei Bedarf eines Pilotbetriebs. |
| SR-40 | Eine Live-Session-Vorlage (Agenda, Materialien) kann einmal erstellt und für mehrere Kohorten und Durchführende wiederverwendet werden | Functional | Eine Live-Session-Vorlage (Agenda, Materialien) wird einmal erstellt und in zwei verschiedenen Kohorten-Terminen wiederverwendet, ohne pro Termin neu angelegt zu werden. |
| SR-41 | Das System liefert AfCJ trainer und admin pro Live-Session-Typ Kennzahlen (Teilnahmequote, Fragehäufigkeit), die als Grundlage für Entscheidungen dienen, welche Sessions echte Live-Fachexpertise brauchen | Data | Für einen abgeschlossenen Live-Session-Typ liefert das System Kennzahlen (Teilnahmequote, Fragehäufigkeit) als Grundlage für die Skalierungsentscheidung, statt dass AfCJ trainer/admin die Daten manuell zusammentragen müssen. |
| SR-42 | Während einer Live-Session kann ein Teilnehmender eine technische Fachfrage an ein KI-gestütztes Assistenzsystem stellen, das aus freigegebenen Wissensquellen antwortet, wenn kein Technik-Trainer anwesend ist | Functional | Während einer Live-Session stellt ein Teilnehmender eine Fachfrage an das Assistenzsystem → Antwort wird ausschließlich aus freigegebenen Wissensquellen (SR zu Wissensquellen-Freigabe) generiert und mit Quellenangabe angezeigt. |
| SR-43 | Eine aufgezeichnete Live-Session kann mit strukturierten Zeitmarken (Wiedereinstiegspunkten) versehen werden, sodass Learner asynchron gezielt an bestimmten Stellen einsteigen können | Functional | Eine aufgezeichnete Live-Session hat mindestens zwei markierte Zeitmarken; ein Learner kann direkt zu einer Zeitmarke springen statt die Aufzeichnung von vorn zu schauen. |
| SR-44 | AfCJ admin kann eigene Rollen mit zugehörigen Permission-Sets anlegen, bearbeiten und Nutzenden zuweisen | Access / Security | Admin legt eine neue Rolle 'Qualitätsprüfer' mit einem eigenen Permission-Set an und weist sie einer Testperson zu → diese Person hat exakt die vergebenen Lese-/Schreibrechte, ohne dass Code geändert wird. |
| SR-45 | Ein Learner kann die Löschung seiner personenbezogenen Daten beantragen; das System löscht oder anonymisiert die Daten unter Wahrung gesetzlich vorgeschriebener Aufbewahrungsfristen innerhalb der DSGVO-Frist | Non-functional | Testantrag auf Löschung eines Learner-Accounts ohne offene AZAV-Aufbewahrungspflicht → personenbezogene Daten werden innerhalb der gesetzlichen Frist gelöscht/anonymisiert. Ein Account mit aktiven AZAV-relevanten Nachweisen wird stattdessen anonymisiert unter Beibehaltung der Nachweisstruktur, nicht sofort vollständig gelöscht — Aufbewahrungsfristen mit AZAV-Anforderung noch mit euch zu klären. |
| SR-46 | Ein Manager sieht für ein TQ-Modul, welcher Anteil der zugehörigen Teilschritte bereits durch verifizierte reale Praxiseinsätze abgedeckt ist, getrennt vom Anteil aus Content-Abschluss | Data | Manager ruft die Ansicht eines TQ-Moduls für einen Mitarbeitenden auf → sieht den Anteil der Teilschritte, die über verifizierte Praxis-Selbstauskünfte (statt über Content) abgedeckt sind, als separaten Prozentwert neben dem Gesamtfortschritt. |
| SR-47 | Das Datenmodell sieht vor, dass ein Learner-Profil künftig um Assessment-Variablen (Vorerfahrung, Abschlüsse, später weichere Faktoren) ergänzt werden kann, ohne die Struktur des Prototyps zu ändern; ein aktiver Assessment-Flow wird erst gebaut, wenn Build next/Later ansteht | Data | Die Learner-Profil-Tabelle enthält bereits (leere) Felder für Assessment-Variablen (u. a. Vorerfahrung, Abschlüsse, Sprachniveau, Motivation); Aktivieren eines Assessment-Flows später erfordert kein Redesign der Tabelle, nur das Befüllen und eine UI davor. |
| SR-48 | AfCJ admin kann für einen Learner ein Profil mit den Basisfeldern E-Mail, Name, Username, Geburtsdatum, Geschlecht und Vorerfahrung (Freitext) anlegen; das Profil ist danach sofort für Magic-Link-Login und Kohortenzuordnung nutzbar | Functional | Admin legt ein Profil mit allen Basisfeldern an → Profil erscheint sofort in der Kohorten-Zuordnung (SR-20) und ein Magic-Link kann dafür ausgelöst werden (SR-16), ohne dass der Learner vorher etwas selbst eingegeben hat. |
| SR-49 | Das System versendet bei Anlage eines Learner-Profils automatisch eine Einladungs-E-Mail mit Magic-Link; Admin muss den Link nicht mehr manuell weiterleiten | Functional | Admin legt ein neues Profil an → Learner erhält innerhalb weniger Minuten automatisch eine E-Mail mit gültigem Zugangslink, ohne dass Admin etwas verschickt. |
| SR-50 | AfCJ admin kann ein SCORM-1.2-Paket als Lektion hochladen (Prototyp: Upload über das Dashboard, Entry-Point wird manuell gesetzt). Unterstützung von SCORM 2004 und automatische Validierung des Manifests (imsmanifest.xml) mit Fehlermeldung sind Later. | Functional | Prototyp: Admin legt ein SCORM-1.2-Paket mit Entry-Point an → Lektion lässt sich im Player öffnen. Later: Upload eines SCORM-2004-Pakets wird erkannt; ein ZIP ohne gültiges imsmanifest.xml wird mit klarer Fehlermeldung abgelehnt, keine kaputte Lektion entsteht. |
| SR-51 | Ein Learner kann ein SCORM-Paket innerhalb der App über einen SCORM-kompatiblen Player mit Runtime-API abspielen | Functional | Learner öffnet eine SCORM-Lektion → Inhalt lädt und ist interaktiv bedienbar (Klicks, Quizfragen etc. funktionieren) innerhalb der App, ohne externen Tab oder Download. |
| SR-52 | Der SCORM-Completion-Status eines Pakets wird automatisch in unit_progress übernommen, ohne manuelles Setzen durch Learner oder Admin | Data | Learner schließt eine SCORM-Lektion ab (cmi.core.lesson_status = completed) → unit_progress-Datensatz wird automatisch auf 'abgeschlossen' gesetzt, ohne dass Learner oder Admin manuell etwas markieren. |
| SR-53 | AfCJ admin kann eine Impersonation-Sitzung für einen anderen Nutzer starten und beenden; jede Impersonation wird protokolliert (wer, wen, wann) | Access / Security | Admin startet Impersonation für einen Learner → sieht die App exakt wie dieser Learner (gleiche Daten, gleiche Sicht), Aktion wird protokolliert (wer hat wann wen impersoniert). Admin beendet Impersonation → zurück zur eigenen Sicht ohne Datenverlust. |
| SR-54 | Das System sieht eine austauschbare "Baukasten"-Struktur für Post-Einsatz-Reflexionsprompts vor (pro Einsatztyp/Fachbezug konfigurierbar), auch wenn im Prototyp nur ein statisches, admin-kuratiertes Format verwendet wird | Data | Datenmodell erlaubt, field_capture perspektivisch mit einem strukturierten Set aus Frage/Antwort-Items zu füllen (nicht nur einem Freitextfeld), ohne die Prototyp-Tabelle neu aufzusetzen. Konkrete LLM-Generierung der Items ist Later, nicht Teil dieses SR. |
| SR-55 | AfCJ admin kann Dateien in ein zentrales Repository hochladen, die von anderen Entities (z. B. Lektionen, Wissensquellen) referenziert werden können | Functional | Admin lädt eine Datei ins Repository hoch → erhält eine ID, die aus einer Lektion heraus referenziert werden kann. Dieselbe Datei kann von mehreren Stellen referenziert werden, ohne erneut hochgeladen zu werden. |
| SR-56 | Das System erlaubt, eine Zielgruppe als Kombination von Filterregeln über Person-Attribute (Geschlecht, Geburtsdatum, Vorerfahrung), Organisationszugehörigkeit und Programmzugehörigkeit zu definieren; Content (Programm/Modul/Kurs/Lektion) kann einer oder mehreren Zielgruppen zugeordnet werden | Data | Admin definiert Zielgruppe "Betrieb = Partnerbetrieb AND Programm = EFK-EE" → alle Personen, die dieser Kombination entsprechen, sehen automatisch den zugeordneten Content. Neue Person, die später hinzukommt und die Kriterien erfüllt, wird automatisch erfasst, ohne manuelle Nachpflege. Offen für die Ausarbeitung: Vorrangregel, falls eine Person mehreren überlappenden Zielgruppen mit widersprüchlicher Sichtbarkeit entspricht. |
| SR-57 | Jede Lektion hat ein Pflichtfeld content_type mit den Werten scorm, live oder repository. Bei scorm referenziert die Lektion ein SCORM-1.2-Paket (scorm_package; im Prototyp, SCORM 2004 ist Later, siehe SR-50). Bei live trägt die Lektion selbst kein Datum/Link — das liegt ausschließlich in der zugehörigen live_session-Instanz aus Group 3. Bei repository referenziert die Lektion mindestens eine Datei- oder Link-Referenz (file_asset). | Data | Anlegen einer Lektion ohne content_type schlägt fehl.
