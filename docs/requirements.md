# System Requirements — AfCJ MVP-Prototyp

Quelle: [MVP April 2027 — Product Development Playbook](https://app.notion.com/p/climatejobsacademy/MVP-April-2027-Product-Development-Playbook-3ce48915565b810db222c7e70679063b) (Notion), Schritt 3, Datenbank "System Requirements". Wörtlicher Export der 53 aktuell in Notion erfassten SRs (IDs 1–57, einzelne IDs durch gelöschte Entwürfe nicht belegt), Stand 2026-09-11. Jede Anforderung trägt hier ihre Notion-`SR-ID` als `SR-xx` — das ist die ID, auf die jeder PR gemäß `CLAUDE.md` verweisen muss.

Alle Anforderungen stehen aktuell auf Notion-Status "Entwurf" (noch nicht auf "Bestätigt" gehoben) — das betrifft die Dokumentation in Notion, nicht notwendigerweise den Umsetzungsstand im Repo. Umsetzungsstand pro SR siehe `traceability.md`.

## Build now (27)

|---|---|---|---|---|

Es existiert kein Formularfeld oder API-Endpunkt, der den Kompetenzstatus direkt schreibt. |
| SR-02 | Ein Learner kann für eine abgeschlossene Praxisaufgabe in der mobilen Feld-Ansicht (PWA) eine Selbstauskunft einreichen, die mindestens einen Teilschritt referenziert und einen Zeitstempel erhält | Functional | Aktiv testen | Learner reicht Selbstauskunft für einen Feldjob ein → Datensatz mit Status 'submitted', Zeitstempel und mind. einer Teilschritt-Referenz ist gespeichert und für den Learner in seinem eigenen Profil sichtbar. |
| SR-03 | Nur AfCJ admin (Prototyp) oder die zuständige Instructor-Rolle (ab MVP) können den Status einer Selbstauskunft von 'submitted' auf 'verified' oder 'rejected' ändern; der einreichende Learner selbst kann seine eigene Selbstauskunft nicht verifizieren | Access / Security | Aktiv testen | Versuch des Learners, die eigene Selbstauskunft zu verifizieren → wird abgelehnt (403 bzw. | SR-06 | Keine API-Antwort, Datenbankabfrage oder Export liefert jemals Datensätze, deren organization_id vom anfragenden Betrieb abweicht — mit Ausnahme AfCJ-eigener (geteilter) Entitäten sowie der Rollen AfCJ admin und AfCJ trainer | Access / Security | Struktur mitbauen | Automatisierter RLS-Test: Nutzer aus Betrieb A fragt Datensätze von Betrieb B ab → leeres Ergebnis, kein Fehler mit Informationsgehalt. Test läuft in CI für jede employer-owned Tabelle. |
| SR-07 | Anwesenheits- und Fortschrittsdatensätze (bestätigte Teilnahme, verifizierte Selbstauskünfte, abgeschlossene Lerneinheiten) sind nach Bestätigung unveränderlich und mit Zeitstempel sowie handelnder Person gespeichert, damit sie AZAV-Nachweisprüfungen standhalten | Non-functional | Struktur mitbauen | Versuch, einen bestätigten Anwesenheits- oder Verifizierungsdatensatz nachträglich zu ändern → vom System verhindert (DB-Trigger). Jeder Datensatz zeigt Zeitstempel und handelnde Person im Export. |
| SR-08 | Schreiboperationen im Feld-Workflow (Selbstauskunft, Foto-Upload) sind klein und in sich abgeschlossen, sodass sie bei unterbrochener Mobilverbindung (schwaches Signal im Zählerschrank) wiederholt werden können, ohne Daten zu verlieren oder zu duplizieren | Non-functional | Struktur mitbauen | Simulierter Verbindungsabbruch während einer Selbstauskunft-Einreichung → Wiederholung des Requests führt zu genau einem gespeicherten Datensatz, nicht zu keinem oder zu doppelten. |
| SR-09 | Für jeden Teilschritt-Typ (Content-Einheit, Live-Veranstaltung, Praxis-Teilschritt) speichert das System einen binären Nachweisstatus (erbracht / nicht erbracht) mit Zeitstempel und der Person, die ihn gesetzt hat | Data | Aktiv testen | AfCJ admin markiert im Backend eine Lektion, einen Kurs, eine Live-Session-Teilnahme und einen Praxis-Teilschritt jeweils als erbracht → alle vier Nachweisstatus sind einheitlich strukturiert (gleiche Felder: Status, Zeitstempel, gesetzt von) abrufbar. |
| SR-12 | Die gesamte Plattform ist übersetzbar (via Sprachauswahl); die Sprachauswahl gilt pro Account und persistiert zwischen Sitzungen | Functional | Struktur mitbauen | Systemsprache auf Ukrainisch stellen → alle Kernbildschirme (Day View, Programmübersicht, Content Library) zeigen ukrainischen Text; fehlende Übersetzungen fallen sichtbar auf Deutsch zurück statt einen Platzhalter oder Fehler zu zeigen. |
| SR-13 | Der Learner sieht eine Tagesansicht, die alle für den aktuellen und folgenden Tag geplanten Aktivitäten (Live-Session, Selbstlerneinheit, Praxistag) chronologisch mit Typ, Uhrzeit und Zugangsweg anzeigt | Functional | Aktiv testen | Learner mit gemischtem Tagesplan (Live-Session um 9 Uhr, Selbstlerneinheit, Praxistag am Nachmittag) sieht alle drei Einträge chronologisch sortiert mit Typ-Kennzeichnung in einer Tagesansicht. |
| SR-14 | Der Learner kann eine Content-Bibliothek einsehen, durchsuchen und nutzen, die alle für sein Qualifikationsprogramm freigegebenen Lerneinheiten einhält | Functional | Aktiv testen | Learner ruft Content Library auf → Liste aller ihm zugänglichen Lerneinheiten (gefiltert nach seinem Qualifikationsprogramm) mit Titel, Typ und Abschlussstatus wird angezeigt; Klick öffnet die Einheit direkt. |
| SR-15 | Für jede geplante Live-Session sieht der Learner Datum, Uhrzeit und einen direkten Beitritts-Link zum externen Video-Tool | Functional | Aktiv testen | Für eine geplante Live-Session zeigt die Detailansicht Datum, Uhrzeit und einen funktionierenden Beitritts-Link; Klick führt direkt zum externen Video-Tool ohne weiteren Login-Schritt. |
| SR-16 | Ein Learner meldet sich ausschließlich per Magic-Link-E-Mail an; es gibt im Prototyp keinen passwortbasierten Login | Functional | Struktur mitbauen | Login-Versuch mit E-Mail-Adresse → Magic-Link-E-Mail wird versendet, Klick auf den Link meldet den Nutzer ohne Passworteingabe an. | SR-17 | Das System trackt und berechnet die kumulierte reale Lernzeit (aus Content-Bearbeitung und Live-Session-Teilnahme); im Prototyp primär zur internen Analyse durch AfCJ, nicht zwingend learner-facing | Data | Struktur mitbauen | Nach Abschluss einer Lerneinheit und einer Live-Session-Teilnahme liegt die kumulierte Lernzeit in Stunden als berechneter Wert vor (aus den einzelnen Aktivitätszeitstempeln, nicht aus einer manuell gepflegten Zahl) und ist für AfCJ admin einsehbar/exportierbar zur Analyse. | SR-19 | AfCJ admin kann im Backend einen neuen Betrieb mit Namen, Ansprechperson und Mitarbeitenden-Accounts anlegen | Functional | Aktiv testen | Admin legt neuen Betrieb mit zwei Mitarbeitenden-Accounts an → beide erhalten eine Magic-Link-Einladung und können sich als Learner der richtigen Organisation anmelden, ohne dass Entwicklung involviert wird. |

| SR-22 | AfCJ admin kann eine aggregierte, betriebsübergreifend vergleichbare Übersicht über Programmstatus und Kompetenzfortschritt aller User in allen Betrieben abrufen | Functional | Struktur mitbauen | Admin ruft die betriebsübergreifende Übersicht auf → Tabelle mit einer Zeile je Betrieb, inkl. | SR-23 | AfCJ admin kann eine Repository-Datei als Wissensquelle (Norm, SOP, Herstellerdokument) markieren und mit einem Freigabestatus versehen; nur freigegebene Quellen werden vom Feld-Guidance-System durchsucht und zitiert | Functional | Struktur mitbauen | Admin markiert eine Repository-Datei als Wissensquelle und setzt Status 'Entwurf' → Dokument erscheint nicht in Guidance-Antworten. | SR-55 | AfCJ admin kann Dateien in ein zentrales Repository hochladen, die von anderen Entities (z. B. | SR-57 | Jede Lektion hat ein Pflichtfeld content_type mit den Werten scorm, live oder repository. Bei scorm referenziert die Lektion ein SCORM-Paket (file_asset). Bei live trägt die Lektion selbst kein Datum/Link — das liegt ausschließlich in der zugehörigen live_session-Instanz. Bei repository referenziert die Lektion mindestens eine Datei- oder Link-Referenz (file_asset) | Data | Aktiv testen | Anlegen einer Lektion ohne content_type schlägt fehl. Eine Lektion mit content_type=live und zusätzlich direkt an der Lektion gesetztem Datum/Join-Link schlägt fehl. Eine Lektion mit content_type=scorm ohne referenziertes SCORM-Paket schlägt fehl. |
